# AI Usage

## Tools used

- **Claude Code (claude-sonnet-4-6 via Claude Code CLI)** — primary development tool used throughout

## Why this tool

Claude Code combines a capable LLM with direct filesystem and shell access, making it well-suited for a full-stack scaffolding task where the output is code rather than prose.

## What was generated vs. written/modified by me

| Area | Generated by AI | Hand-written / reviewed |
|------|----------------|------------------------|
| NestJS entity, DTOs, service, controller | AI-generated from spec | Reviewed; phone regex manually verified against AU numbering plan |
| `app.module.ts`, `main.ts` | AI-generated | Reviewed |
| Next.js pages (`contact`, `thank-you`, `contacts`) | AI-generated | Reviewed for correctness |
| SWR hooks (`useContacts`, `useCreateContact`) | AI-generated | Reviewed |
| `ContactCard`, `ContactsList`, `Card` components | AI-generated | Reviewed |
| `lib/api.ts`, `lib/types.ts` | AI-generated | Reviewed |
| Dockerfiles + docker-compose.yml | AI-generated | Debugged manually (port conflicts, missing `public/` dir, `.mjs` config requirement) |
| This file + README.md | AI-drafted | Content (assumptions, improvements, rationale) reflects genuine design decisions |
| CLAUDE.md spec | Human-authored spec translated from the PDF brief | — |

## What I used alongside the AI

- The official NestJS, TypeORM, Next.js, react-hook-form, and zod documentation for reference
- `curl` to manually verify API responses during acceptance checks
- Docker Desktop for container runtime

## Notes

All code was reviewed before committing. Bugs surfaced during Docker builds (the `public/` copy step, `next.config.ts` vs `.mjs`, nested `.git` in the web scaffold) were diagnosed and fixed manually. The AI did not have browser access during development — UI correctness was verified via `curl` and HTML inspection.
